# Task 0, version A: credit usage of an "on update" NBA props feed

**Run:** Nov 17, 2026, 20:32 to 21:32 UTC · **Author:** Josue Martinez · **Data:** `src/live_feed/runs/version_a/20261117T203215Z/` (local, not in git)

## Short answer

- **Is there a way to only call the API when an odd is updated?** No. The Odds API has no push, websocket or webhook. Every update has to be polled.
- **Closest thing, built and tested:** poll the cheap `/markets` endpoint (1 credit) to see which markets were updated, then fetch only those. In practice the API flagged every watched market as updated on every poll, so this never skipped a fetch.
- **Result:** keeping 3 prop markets of 1 NBA game up to date every 2 minutes cost **120 credits per hour**. Plain polling every 2 minutes, without the check, would cost 90.
- **Tier:** at NBA volume (about 220 games a month) props need well over 100K credits a month. The **5M plan ($119/month)** is the first tier that fits, with room for more markets and sports (see the estimate below).

## Latency (bonus)

The API doesn't say when a book changed a price. The closest timestamp is the market's `last_update`, which is when The Odds API last read the book.

| From → to | Median | Max | Samples |
|---|---|---|---|
| API `last_update` → received by the feed | 35 s | 116 s | 627 changes |
| API `last_update` → loaded by the props dashboard | 21 s | 65 s | 22 pulls (dashboard joined mid-run) |
| Received by the feed → loaded by the dashboard | 1.0 s | 2.0 s | 22 pulls |

Almost all of the delay is the poll interval: a change waits up to 2 minutes for the next poll. Polling every minute would roughly halve it and double the credits.

## Why version A doesn't save credits

1. `last_update` moves whenever The Odds API re-reads a book, not when a price changes. All markets of one book share the same time, so the check flags everything.
2. Prices really do change almost every poll before tip-off (2 of 29 fetches had no change), so even a perfect "only on change" signal would have saved very little here.
3. The check costs 1 credit per game per poll. With 3 markets that is a third more than just fetching (4 vs 3 credits a poll).

Version A could only pay off with many markets per game and long quiet stretches, which is not what NBA props look like on game day.

## Monthly estimate (to choose a tier)

Formula, per game and per hour of coverage at a 2-minute interval: version A = 30 × (1 + markets); plain polling = 30 × markets.

Assumptions (not measured): about **220 NBA games a month** (1,230 regular-season games over about 5.5 months), 1 region (`us`), props kept live for the last 2 or 6 hours before tip-off.

| Markets per game | Hours per game | Version A credits/month | Plain 2-min polling credits/month |
|---|---|---|---|
| 3 | 2 | 52,800 | 39,600 |
| 3 | 6 | 158,400 | 118,800 |
| 10 | 2 | 145,200 | 132,000 |
| 10 | 6 | 435,600 | 396,000 |

Plans on Nov 17, 2026 ([the-odds-api.com](https://the-odds-api.com/#get-access)): Free 500 · 20K $30 · 100K $59 · **5M $119** · 15M $249.

Only the smallest scenario (3 markets, 2 hours, plain polling) fits in 100K. Anything with more markets, more hours, a 1-minute interval near tip-off (version B) or other sports (tennis, soccer) needs the 5M plan.

## Limits of this test

- One game and one hour, about 3 hours before tip-off. Odds usually move more close to tip-off, so these numbers may be on the low side.
- Monthly figures are extrapolated from that hour, not measured.
- Player lines are matched by name (`description`); the API gives no player id. Production needs a player mapping table.
